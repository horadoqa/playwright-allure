Basics — Navigation & First Assertions

Every test starts with navigating to a page and verifying something is there. Playwright auto-waits for elements, so no sleep() needed.

🔑 Key Concept: page.goto('/') uses the baseURL from config. All expect() assertions auto-retry until the timeout (default 5s).
page.goto()
→
Find Element
→
expect() Assert
→
✅ Pass / ❌ Fail
📝 Navigate & Assert Title
import { test, expect } from '@playwright/test';

test('should navigate to the app', async ({ page }) => {
  await page.goto('/');                          // uses baseURL from config

  await expect(page).toHaveTitle(/TodoMVC/);    // regex match on title

  await expect(                                   // find heading by role
    page.getByRole('heading', { name: 'todos' })
  ).toBeVisible();
});

test('should have correct URL', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveURL(/todomvc/);       // assert URL pattern
});

Locators — Finding Elements

Locators are the core of Playwright. They auto-wait, auto-retry, and are strict by default (fail if multiple matches). Prefer semantic locators.

💡 Priority Order: getByRole → getByText → getByTestId → getByPlaceholder → locator(css). Role-based locators are the most resilient to UI changes.
🎯 Locator Strategies
Strategy Code When to Use
By Role ⭐ page.getByRole('textbox', { name: '...' }) Best practice — semantic & accessible
By Placeholder page.getByPlaceholder('What needs...') Input fields with placeholder text
By Text page.getByText('todos') Visible text content
By Test ID page.getByTestId('new-todo') When you control the markup
By Label page.getByLabel('Email') Form fields with labels
CSS Selector page.locator('.new-todo') Fallback — less resilient
🔗 Chaining Locators
// Narrow down: find items WITHIN a container
const todoList = page.locator('.todo-list');
const firstItem = todoList.locator('li').first();
await expect(firstItem).toContainText('Buy milk');

// .first(), .last(), .nth(index) — pick from multiple matches
📝 All Locator Examples
// By Role (recommended)
const input = page.getByRole('textbox', { name: 'What needs to be done?' });

// By Placeholder
const input2 = page.getByPlaceholder('What needs to be done?');

// By Text
const heading = page.getByText('todos');

// By CSS (fallback)
const input3 = page.locator('.new-todo');

Actions — User Interactions

Simulate real user behavior: typing, clicking, double-clicking, hovering, and keyboard shortcuts. Playwright waits for elements to be actionable before performing actions.

🔑 Auto-Actionability: Before each action, Playwright checks the element is visible, enabled, stable, and not obscured. No manual waits needed.
⌨️ Type & Submit
const input = page.getByPlaceholder('What needs to be done?');

await input.fill('Learn Playwright');    // clear + type (fast)
await input.press('Enter');              // press a key

// Verify
await expect(page.locator('.todo-list li')).toHaveCount(1);
await expect(page.locator('.todo-list li')).toHaveText(['Learn Playwright']);
🖱️ Click, Double-Click, Hover
// Single click — toggle a checkbox
await page.locator('.todo-list li .toggle').click();

// Double-click — enter edit mode
await page.locator('.todo-list li label').dblclick();

// Edit: clear and retype
const editInput = page.locator('.todo-list li .edit');
await editInput.fill('Updated text');
await editInput.press('Enter');

// Hover — reveal hidden buttons
await page.locator('.todo-list li').hover();
🔄 Loop — Add Multiple Items
const items = ['Buy groceries', 'Clean house', 'Walk the dog'];
const input = page.getByPlaceholder('What needs to be done?');

for (const item of items) {
  await input.fill(item);
  await input.press('Enter');
}

await expect(page.locator('.todo-list li')).toHaveCount(3);
await expect(page.locator('.todo-list li')).toHaveText(items);

Assertions — Verifying State

All expect() assertions auto-retry until the condition is met or the timeout expires (default 5s). This eliminates flaky tests caused by timing issues.

📋 Assertion Cheat Sheet
Assertion What It Checks
toBeVisible() Element is visible on page
toBeHidden() Element is not visible
toHaveText('...') Exact text content
toContainText('...') Partial text match
toHaveCount(n) Number of matched elements
toHaveClass(/pattern/) CSS class matches regex
toBeChecked() Checkbox/radio is checked
toHaveURL(/pattern/) Page URL matches
toHaveTitle(/pattern/) Page title matches
toHaveScreenshot() Visual regression comparison
✅ Common Assertions in Action
// Visibility
await expect(page.locator('.todo-list')).toBeVisible();
await expect(page.locator('.nonexistent')).toBeHidden();

// Text content
await expect(page.locator('.todo-list li').first()).toHaveText('Task A');
await expect(page.locator('.todo-list li').first()).toContainText('Task');

// Count
await expect(page.locator('.todo-list li')).toHaveCount(2);

// CSS class
await expect(page.locator('.todo-list li').first()).toHaveClass(/completed/);

// Checkbox state
await expect(checkbox).not.toBeChecked();
await checkbox.click();
await expect(checkbox).toBeChecked();
🧪 Soft Assertions (Collect Multiple Failures)
// Soft assertions don't stop the test on failure — all run, then report
await expect.soft(page.locator('.todo-list li')).toHaveCount(2);
await expect.soft(page.locator('.todo-count')).toContainText('2 items left');

// Negation with .not
await expect(element).not.toBeVisible();

Hooks & Custom Fixtures

Hooks run setup/teardown code around tests. Fixtures let you create reusable, composable test contexts — Playwright's most powerful pattern for DRY tests.

🔑 Hooks vs Fixtures: Hooks (beforeEach, afterEach) are simple setup/teardown. Fixtures (test.extend) are reusable, composable, and can provide custom data or state to tests.
🪝 Lifecycle Hooks
test.describe('My Suite', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/');                // runs before EACH test
  });

  test.afterEach(async ({ page }) => {
    // cleanup if needed (Playwright handles most cleanup)
  });

  test('page is ready', async ({ page }) => {
    await expect(page.getByRole('heading', { name: 'todos' })).toBeVisible();
  });
});
🧩 Custom Fixtures with test.extend
// Create a fixture that pre-populates todos
const testWithTodos = test.extend<{ todosPage: void }>({
  todosPage: async ({ page }, use) => {
    // ── SETUP ──
    await page.goto('/');
    const input = page.getByPlaceholder('What needs to be done?');
    await input.fill('Fixture Todo 1'); await input.press('Enter');
    await input.fill('Fixture Todo 2'); await input.press('Enter');

    await use();  // ← hand control to the test

    // ── TEARDOWN ── (runs after the test)
  },
});

testWithTodos('todos are pre-populated', async ({ page, todosPage }) => {
  await expect(page.locator('.todo-list li')).toHaveCount(2);
});

Page Object Model (POM)

Encapsulate page interactions into reusable classes. This keeps tests clean, readable, and easy to maintain when the UI changes.

💡 Why POM? If a CSS selector changes, you update it in ONE place (the page class) instead of every test file. Tests read like user stories.
Page Class
→
Locators as Properties
→
Actions as Methods
→
Clean Tests
📦 todo-page.ts — The Page Object
import { type Locator, type Page, expect } from '@playwright/test';

export class TodoPage {
  readonly page: Page;
  readonly newTodoInput: Locator;
  readonly todoItems: Locator;
  readonly todoCount: Locator;

  constructor(page: Page) {
    this.page = page;
    this.newTodoInput = page.getByPlaceholder('What needs to be done?');
    this.todoItems = page.locator('.todo-list li');
    this.todoCount = page.locator('.todo-count');
  }

  async goto()                    { await this.page.goto('/'); }
  async addTodo(text: string)     { await this.newTodoInput.fill(text); await this.newTodoInput.press('Enter'); }
  async completeTodo(i: number)  { await this.todoItems.nth(i).locator('.toggle').click(); }
  async deleteTodo(i: number)    {
    await this.todoItems.nth(i).hover();
    await this.todoItems.nth(i).locator('.destroy').click();
  }
  async filterByActive()         { await this.page.getByRole('link', { name: 'Active' }).click(); }
  async filterByCompleted()      { await this.page.getByRole('link', { name: 'Completed' }).click(); }
  async expectTodoCount(n: number)       { await expect(this.todoItems).toHaveCount(n); }
  async expectTodoTexts(t: string[])   { await expect(this.todoItems).toHaveText(t); }
}
🧪 todo-page.spec.ts — Clean Tests Using POM
import { TodoPage } from './todo-page';

test.describe('Page Object Model', () => {
  let todoPage: TodoPage;

  test.beforeEach(async ({ page }) => {
    todoPage = new TodoPage(page);
    await todoPage.goto();
  });

  test('add and verify todos', async () => {
    await todoPage.addTodo('Learn POM pattern');
    await todoPage.addTodo('Write clean tests');
    await todoPage.expectTodoCount(2);
    await todoPage.expectTodoTexts(['Learn POM pattern', 'Write clean tests']);
  });

  test('complete and filter', async () => {
    await todoPage.addTodo('Active task');
    await todoPage.addTodo('Done task');
    await todoPage.completeTodo(1);
    await todoPage.filterByActive();
    await todoPage.expectTodoCount(1);
  });

  test('delete a todo', async () => {
    await todoPage.addTodo('To be deleted');
    await todoPage.addTodo('To remain');
    await todoPage.deleteTodo(0);
    await todoPage.expectTodoTexts(['To remain']);
  });
});

API Testing & Network Interception

Playwright can make HTTP requests directly (no browser needed) and intercept/mock network traffic for faster, more reliable tests.

🔑 Two Modes: Use request fixture for direct API calls (no browser). Use page.route() to intercept, mock, or block network requests in browser tests.
📡 Direct API Requests (No Browser)
test('GET request', async ({ request }) => {
  const response = await request.get('https://jsonplaceholder.typicode.com/todos/1');

  expect(response.ok()).toBeTruthy();
  expect(response.status()).toBe(200);

  const body = await response.json();
  expect(body).toHaveProperty('id', 1);
  expect(body).toHaveProperty('title');
});

test('POST request', async ({ request }) => {
  const response = await request.post('https://jsonplaceholder.typicode.com/todos', {
    data: { title: 'New todo', completed: false, userId: 1 },
  });
  const body = await response.json();
  expect(body).toHaveProperty('title', 'New todo');
});
🎭 Network Mocking & Interception
// Mock an API response
await page.route('**/api/todos', (route) => {
  route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify([{ id: 1, title: 'Mocked Todo', completed: false }]),
  });
});

// Block resources for faster tests
await page.route(/(\.png|\.jpg|\.woff2)/, (route) => route.abort());

// Let requests through (useful for logging)
await page.route('**/*.css', (route) => route.continue());

Advanced Patterns

Screenshots, visual regression, multi-tab handling, localStorage, waiting strategies, tags, and annotations.

📸 Screenshots & Visual Regression
// Full page screenshot
await page.screenshot({ path: 'screenshots/homepage.png', fullPage: true });

// Element screenshot
const header = page.locator('header');
await header.screenshot({ path: 'screenshots/header.png' });

// Visual regression — compares against baseline
await expect(page).toHaveScreenshot('homepage.png', {
  maxDiffPixelRatio: 0.05,  // allow 5% pixel difference
});
🗂️ Multiple Tabs & Pages
test('handle new tab', async ({ page, context }) => {
  await page.goto('/');

  // Wait for new page event + trigger it
  const [newPage] = await Promise.all([
    context.waitForEvent('page'),
    page.evaluate(() => window.open('https://demo.playwright.dev/todomvc/')),
  ]);

  await newPage.waitForLoadState();
  await expect(newPage).toHaveTitle(/TodoMVC/);
});
💾 localStorage & Storage State
// Set localStorage
await page.evaluate(() => {
  localStorage.setItem('test-key', 'test-value');
});

// Read localStorage
const value = await page.evaluate(() => localStorage.getItem('test-key'));
expect(value).toBe('test-value');
⏳ Waiting Strategies
// Wait for network idle
await page.goto('/', { waitUntil: 'networkidle' });

// Wait for a specific response
const responsePromise = page.waitForResponse(
  (resp) => resp.url().includes('todomvc') && resp.status() === 200
);
await page.goto('/');
const response = await responsePromise;
🏷️ Tags & Annotations
// Mark a test as slow (triples the timeout)
test('slow test', async ({ page }) => {
  test.slow();
  // ... long-running test
});

// Skip conditionally
test('skip on webkit', async ({ page, browserName }) => {
  test.skip(browserName === 'webkit', 'Not supported on WebKit yet');
});

// Tagged tests — run with: npx playwright test --grep @smoke
test('smoke test @smoke', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveTitle(/TodoMVC/);
});

Playwright vs Selenium — Pros & Cons

Both are powerful E2E testing tools, but they have very different architectures and trade-offs. Here's a detailed comparison.

📊 Feature Comparison
Feature Playwright Selenium
Architecture Direct browser protocol (CDP/BiDi) WebDriver protocol via driver binary
Languages JS/TS, Python, Java, C# JS, Python, Java, C#, Ruby, Kotlin
Browsers Chromium, Firefox, WebKit Chrome, Firefox, Safari, Edge, IE
Auto-Wait ✅ Built-in for all actions ❌ Manual waits required
Speed Very fast (no HTTP overhead) Slower (HTTP-based protocol)
Parallel Tests ✅ Built-in, per-test isolation Requires Selenium Grid or TestNG
API Testing ✅ Built-in request fixture ❌ Needs external libraries
Network Mocking ✅ Built-in page.route() ❌ Needs proxy tools
Screenshots ✅ Full page + element + visual diff ✅ Full page only (basic)
Video Recording ✅ Built-in ❌ Needs external tools
Trace Viewer ✅ Built-in time-travel debugger ❌ Not available
Mobile Testing Emulation only (viewports, touch) Real devices via Appium
iframes ✅ First-class support ✅ Supported (switch-based)
Multi-tab/window ✅ Native support ⚠️ Limited, manual handling
Community Age Since 2020 (Microsoft) Since 2004 (mature ecosystem)
CI/CD ✅ Docker images, GitHub Actions ✅ Widely supported
Test Runner ✅ Built-in (@playwright/test) ❌ Needs JUnit, TestNG, pytest, etc.
Codegen ✅ npx playwright codegen ⚠️ Selenium IDE (browser extension)

🎭 Playwright — Pros

  • Auto-waiting eliminates flaky tests — no sleep() or explicit waits
  • Blazing fast execution via direct browser protocol (no HTTP overhead)
  • Built-in test runner, assertions, fixtures, and parallel execution
  • Network mocking and API testing out of the box
  • Trace viewer with time-travel debugging (screenshots at every step)
  • Built-in video recording and screenshot comparison
  • Each test gets a fresh browser context (true isolation)
  • Codegen tool records user actions and generates test code
  • First-class TypeScript support
  • Cross-browser with a single API (Chromium, Firefox, WebKit)

🎭 Playwright — Cons

  • Newer ecosystem — smaller community and fewer third-party plugins
  • No real mobile device testing (emulation only, no Appium equivalent)
  • Fewer language bindings than Selenium (no Ruby, no Kotlin)
  • Uses bundled browser binaries (larger disk footprint)
  • Less enterprise adoption history compared to Selenium
  • WebKit support is Playwright's own build, not actual Safari

🔧 Selenium — Pros

  • 20+ years of maturity — battle-tested in enterprise environments
  • Massive community, extensive documentation, and tutorials
  • Supports real mobile devices via Appium integration
  • More language bindings (Java, Python, C#, Ruby, JS, Kotlin)
  • W3C WebDriver standard — browser-vendor supported
  • Selenium Grid for distributed/parallel execution at scale
  • Works with actual browser installations (no bundled binaries)
  • Huge ecosystem of third-party tools and frameworks

🔧 Selenium — Cons

  • No auto-waiting — requires explicit/implicit waits (flaky tests)
  • Slower execution due to HTTP-based WebDriver protocol
  • No built-in test runner — needs JUnit, TestNG, pytest, etc.
  • No built-in network mocking or API testing
  • No built-in video recording or trace viewer
  • Complex setup: browser + driver binary version matching
  • No built-in parallel execution (needs Grid or test framework config)
  • Verbose code for common tasks compared to Playwright
  • No built-in screenshot comparison / visual regression
⚡ TL;DR: Choose Playwright for modern web apps where speed, reliability, and developer experience matter most. Choose Selenium when you need real mobile device testing, broader language support, or are working in an enterprise with existing Selenium infrastructure.
🤔 When to Pick Which?
Scenario Recommendation
New project, modern web app Playwright — faster setup, better DX
Need real mobile device testing Selenium + Appium
Team uses Ruby or Kotlin Selenium — broader language support
API + UI testing in one framework Playwright — built-in API testing
Existing Selenium Grid infrastructure Selenium — leverage existing setup
Flaky test issues Playwright — auto-wait solves most flakiness
Visual regression testing Playwright — built-in screenshot comparison
Cross-browser + cross-device Both work, but Playwright is simpler to configure
